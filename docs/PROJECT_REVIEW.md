# 项目评审报告：FastAPI Starter

> 评审时间：2026-05-20
> 评审目标：评估本项目面向**大二学生找日常实习**场景的竞争力、短板与改进方向

---

## 一、总体评价

**一句话结论：这是一个超出大二学生平均水平的、有竞争力的后端 + AI 工程项目，不是玩具项目。**

这个项目最难得的地方在于——它不是"调个 API 聊聊天"的套壳 Demo，而是有完整后端工程结构、有真实业务链路、有可观测性体系、有工程化保障的**系统级项目**。对于大二学生找日常实习来说，这个项目的广度已经足够，部分深度甚至超出预期。

### 评级（满分 5★）

| 维度 | 评分 | 说明 |
|------|------|------|
| 后端工程能力 | ★★★★☆ | 分层架构、依赖注入、ORM、迁移、异常处理都很规范 |
| AI 应用能力 | ★★★★☆ | RAG 完整链路 + Tool Calling 多轮调用，不是套壳 |
| 工程化水平 | ★★★★☆ | CI/CD、Docker、pre-commit、测试覆盖、结构化日志 |
| 可观测性 | ★★★★☆ | Prometheus + Grafana + LLM 日志 + Request ID |
| 安全性 | ★★★☆☆ | JWT/bcrypt 基础安全有，但缺少更多安全实践 |
| 前端/展示 | ★★☆☆☆ | Demo 页面可用但不精美，缺少录屏/GIF |
| 独特性 | ★★★☆☆ | 功能组合不错，但每个单项都不是独创 |
| 简历价值 | ★★★★☆ | 对实习面试来说已经是一个很能打的项目 |

## 二、这个项目在面试中是什么水平？

### 相比大二学生平均水平

大多数大二学生的"后端项目"停留在：
- 简单的 CRUD（增删改查）
- 没有用户体系或 JWT
- 单机单体，不会用消息队列
- 没有测试
- 没有 Docker

**这个项目远超上述水平。** 它覆盖了 RAG、Tool Calling、异步任务、可观测性这些通常在"高级"项目中才会出现的能力。

### 是否会被面试官鉴定为玩具项目？

**大概率不会，但有三个潜在风险：**

1. **"这是你一个人写的吗？"** —— 功能太多，面试官可能怀疑是否参考了大量现成代码或 AI 生成。这是最大的风险。
2. **"你对每一行代码都理解吗？"** —— 广度过大，如果面试者只懂表面不懂细节，反而会露怯。
3. **"为什么不做前端？"** —— 面试官可能期待一个能演示的完整产品，而不是只有后端 API。

### 是否会过难？

**对大二学生来说，这个项目的难度适中偏上。** 这是一个**优点**，不是问题。面试官不会要求大二学生达到 P8 级别，这个项目的复杂度正好能展示潜力。

关键是：
- **能讲清楚**：RAG 链路为什么需要异步？pgvector 怎么算相似度？JWT 和 Session 的区别？
- **能指出不足**：知道哪里可以更好，比假装完美更有说服力
- **能展示热情**：能说出下一步想做什么，为什么想做

## 三、优点总结

### 3.1 架构设计（最大亮点）

- **严格的分层架构**：API → Service → Model，职责清晰，代码可维护性强
- **依赖注入规范**：get_db、get_current_user 等 DI 函数设计合理
- **SQLAlchemy 2.0 新式语法**：使用 `select()` 而非废弃的 `session.query()`，表明对新技术跟进意识

### 3.2 AI 落地（核心卖点）

- **RAG 完整链路**：上传 → 异步切分 → Embedding → pgvector 检索 → Reranker 重排，端到端闭环
- **Tool Calling**：5 个工具，有两轮调用逻辑，不是示意的"Hello World"
- **多租户 BYOK**：支持用户自定义 LLM 配置，有生产级思维
- **SSE 流式输出**：Chat 和 RAG 都支持，体现对实时通信的理解

### 3.3 工程化（拉开差距的地方）

- **121 个单元测试** + conftest 支持 SQLite/PostgreSQL 双模式
- **GitHub Actions CI**：PostgreSQL 集成测试 + Docker 构建验证
- **pre-commit hooks**（ruff lint + format）
- **Alembic 数据库迁移**：8 个版本，有完整的迁移历史
- **Docker Compose 一键启动**：8 个容器编排

### 3.4 可观测性

- **Prometheus + Grafana**：预置看板
- **Request ID 链路追踪**
- **LLM 调用日志**：token 消耗、成本估算、延迟、状态
- **结构化 JSON 日志**（可选）
- **健康检查探针**：DB/Redis/Ollama 依赖状态

### 3.5 安全性

- **JWT + bcrypt** 基础鉴权
- **Fernet 加密**：API Key 加密存储
- **滑动窗口限流**：Redis ZSET 实现，自动降级
- **用户级数据隔离**：文档和任务按 owner_id 过滤

## 四、不足与风险

### 4.1 展示层面的短板（最紧急）

| 问题 | 影响程度 | 说明 |
|------|----------|------|
| **没有在线 Demo** | 🔴 高 | 面试官不会去 `docker compose up`，看不到效果 = 没有 |
| **没有操作录屏/GIF** | 🔴 高 | README 截图是静止的，缺少动起来的体验 |
| **Demo 页面简陋** | 🟡 中 | demo.html 功能有但 UI 粗糙，不像"产品" |
| **架构图不够直观** | 🟡 中 | 现有 mermaid 图是简化的，缺少完整请求链路 |

### 4.2 技术深度的不足

| 问题 | 影响程度 | 说明 |
|------|----------|------|
| **测试都是单元/集成测试，缺少压力测试结果** | 🟡 中 | 有 locust 脚本但没有运行报告 |
| **Reranker 是可选的，不一定能跑** | 🟡 中 | sentence-transformers 依赖需要单独安装 |
| **Chat 工具调用不支持流式** | 🟡 中 | 流式和非流式的代码路径分离，工具调用时只能阻塞 |
| **没有用户注册验证/邮件确认** | 🟢 低 | 注册即激活，缺少邮箱验证环节 |
| **限流只覆盖了 Chat 接口** | 🟢 低 | 其他接口没有限流保护 |
| **pgvector 没有建 HNSW 索引** | 🟢 低 | 数据量大时检索性能会下降 |

### 4.3 容易被质疑的点

| 质疑 | 应对建议 |
|------|----------|
| "这个项目是不是 AI 生成的？" | 熟悉 CLAUDE.md 中的每一条规定，能解释为什么这么分层 |
| "这些功能你都会实现吗？" | 至少能讲清楚 RAG 和 Tool Calling 的核心代码路径 |
| "为什么用 SQLite 跑测试？" | 能解释 conftest.py 双模式设计，以及 SQLite 不支持 pgvector 对测试的影响 |
| "为什么没有部署？" | 准备一个合理的理由（如"学校项目，想着先让功能完整再部署"） |
| "5 个工具太简单了？" | 能说出下一个你想做的工具是什么，为什么 |

### 4.4 代码本身的改进空间

- `observability.py` router 中混合了 `db.query()`（旧式语法）和 `select()`（新式语法），不一致
- 某些 router 中的错误处理可以直接抛出 `HTTPException`，而不是通过 `AppException` 统一处理
- 缺少对超时、重试、熔断等生产级容错机制的考虑
- 没有使用 async SQLAlchemy 引擎（当前是同步的）

## 六、面试可能被问到的问题清单

准备以下问题的答案，比完善代码更重要：

### 架构与设计
- ❓ 为什么选择分层架构？每一层的职责是什么？
- ❓ FastAPI 的依赖注入是怎么工作的？`Depends()` 的原理？
- ❓ 为什么用 Celery 而不是直接在线程里跑？

### RAG
- ❓ 文档切分的 chunk_size 为什么选 500？chunk_overlap 的作用？
- ❓ 如何让检索结果只返回当前用户的文档？（owner_id 过滤）
- ❓ BGE-Reranker 和普通的向量检索有什么区别？为什么需要两步？

### Tool Calling
- ❓ 大模型返回 tool_calls 之后，你的代码怎么处理多轮调用？
- ❓ 如果模型第一轮返回了 3 个工具调用，怎么并发的？
- ❓ 为什么 `calculate` 工具要用 eval？安全性怎么保证？

### 可观测性
- ❓ LLM 调用日志里 estimated_cost_usd 怎么算的？有什么局限？
- ❓ Request ID 是怎么注入到日志和响应头里的？
- ❓ Prometheus 仪表盘主要展示了哪些指标？

### 安全性
- ❓ API Key 是怎么加密的？为什么用 Fernet 而不是直接 AES？
- ❓ 限流器用的什么数据结构？为什么 Redis 挂了还能正常工作？

## 七、简历描述建议

### 推荐写法

```
基于 FastAPI + PostgreSQL(pgvector) + Redis + Celery + Ollama 构建的个人知识库与任务执行 Agent 后端系统。

核心能力：
- RAG 知识库：支持多格式文档上传（.txt/.md/.pdf），Celery 异步执行文本切分与向量化，pgvector 余弦检索 + BGE-Reranker 重排
- LLM Agent：兼容 OpenAI 接口的多轮对话，5 个 Tool Calling 工具，多租户 BYOK（API Key 加密存储）
- 可观测体系：Prometheus + Grafana 监控大盘，LLM 调用日志（token/耗时/成本），Request ID 链路追踪
- 工程保障：121 个单元测试，CI/CD（GitHub Actions + PostgreSQL 集成测试），Docker Compose 一键部署，Alembic 迁移
```

### 不推荐写的
- ❌ "精通 xxx" —— 大二学生说精通很危险
- ❌ 堆砌技术名词 —— 面试官会追问细节
- ❌ 夸大功能规模 —— 诚实比炫技重要

## 九、最后的话

这个项目对一位大二学生来说，**已经是一个非常拿得出手的作品**。它不是玩具，它有真实的后端工程深度——RAG 完整链路、Tool Calling 多轮调用、可观测性体系、CI/CD、Docker 编排，这些都不是"入门项目"会有的东西。

最大的风险不是"项目太简单"，而是"项目太多，面试者自己说不清楚"。**建议花时间把每一条链路从用户请求到数据库落地的完整路径走一遍，确保能流畅讲解。**

最有效的改进只有两件事：
1. **部署到线上**（成本几乎为 0，但面试效果提升最大）
2. **录制操作 Demo**（一张动图胜过千言万语）

剩下的完善都是锦上添花，不影响你对面试官的"第一印象"。
