# 项目 MVP 文档

## 1. 文档目的

这份文档用于定义当前项目在“投递实习 / 展示作品”场景下的最小可行版本（MVP），明确：

- 这个项目最核心要展示的能力是什么
- 哪些功能已经足够构成一个完整闭环
- 哪些内容是当前阶段可以暂时不做的
- README、Demo、截图和讲解应该围绕什么来组织

这不是完整产品需求文档，而是面向“项目展示”和“投递包装”的 MVP 说明。

## 2. 项目一句话定义

一个基于 `FastAPI + PostgreSQL + Redis + Celery + Ollama` 的个人知识库与任务执行 Agent 后端系统，支持用户鉴权、文档问答、工具调用、异步处理与可观测。

## 3. MVP 目标

当前 MVP 的目标不是做成复杂 AI 平台，而是清晰证明下面 4 件事：

1. 我能独立完成一个标准 Python 后端项目
2. 我能把 LLM 能力接入真实后端业务链路
3. 我能实现 RAG、Tool Calling、异步任务这些 AI 应用核心能力
4. 我有基本工程化意识，包括部署、监控、日志与可观测

## 4. 目标用户

当前 MVP 不是面向真实商业用户优先，而是面向下面两类“评审者”：

- 招聘方：HR、Boss 直聘上的业务负责人、面试官
- 技术评审者：看到仓库、README、Demo 的后端或 AI 应用工程师

所以这个 MVP 最重要的不是功能越多越好，而是：

- 一眼看懂
- 能跑起来
- 能讲清楚
- 能证明工程能力

## 5. MVP 核心场景

MVP 只需要讲清楚 3 条主场景。

### 场景 A：用户登录并使用受保护接口

说明项目不是匿名聊天 demo，而是有用户体系的后端服务。

用户动作：

- 注册或登录
- 获取 JWT Token
- 携带 Token 调用业务接口

要证明的能力：

- 用户系统
- JWT 鉴权
- 标准 API 设计

### 场景 B：上传文档并完成知识库问答

这是整个项目最重要的 AI 展示闭环。

用户动作：

- 上传文档
- 系统异步完成切分和向量化
- 用户发起问题
- 系统执行检索并返回答案
- 返回结果带引用片段或文档来源

要证明的能力：

- RAG
- 向量检索
- 异步任务
- AI 能力和业务接口结合

### 场景 C：通过 Agent 调用工具执行任务

这是项目和普通 RAG Demo 拉开差距的地方。

用户动作：

- 向聊天接口输入一个带任务意图的问题
- Agent 判断需要调用工具
- 系统执行任务创建或查询
- 返回最终结果

要证明的能力：

- Tool Calling
- 多步业务链路
- LLM 与已有业务系统联动

## 6. MVP 最小功能范围

下面这些功能已经足够构成当前项目的 MVP。

### 必须有

- 用户注册、登录、JWT 鉴权
- 基础任务管理接口
- 文档上传接口
- 文档切分、向量化、检索问答
- 至少 2 到 3 个可用工具函数
- 至少 1 条可跑通的 Agent 工具调用链路
- Celery 异步任务处理
- Docker Compose 一键启动
- Prometheus + Grafana 基础监控
- LLM 调用日志或统计能力

### 可以弱化但最好保留

- Swagger / OpenAPI 自动文档
- Alembic 数据库迁移
- Pytest 基础测试
- 简单的错误处理和日志追踪

## 7. 当前 MVP 不必强求的内容

下面这些内容有加分，但不是当前投递阶段的 MVP 必需项：

- 漂亮前端页面
- 多租户系统
- 复杂权限模型
- 多模型路由策略
- 大规模评测平台
- 云端正式部署
- 非常复杂的 Agent Planner

结论很简单：

当前阶段你不是要证明“系统有多大”，而是要证明“我能把一条完整 AI 后端链路做扎实”。

## 8. MVP 成功标准

如果下面这些点都能被截图、录屏或命令演示证明，这个项目就已经达到投递可用的 MVP 标准。

### 功能成功标准

- 可以完成注册和登录
- 可以带 Token 调用受保护接口
- 可以上传文档并成功入库
- 可以基于知识库完成一次问答
- 回答里能展示引用来源
- 可以通过 Agent 触发一次工具调用
- 可以看到任务创建或查询结果

### 工程成功标准

- `docker compose up -d --build` 后系统可以启动
- Swagger 可访问
- `/metrics` 可访问
- Grafana 面板可看到请求数据
- 至少有一条 LLM 调用日志或统计记录

### 展示成功标准

- README 能说明项目定位、架构、启动方式和演示路径
- 仓库中有截图或 GIF
- 能用 30 秒到 1 分钟讲清楚项目主链路

## 9. 推荐展示主链路

README 和 Demo 都应该优先围绕下面这条主链路展开：

1. 用户登录并获取 Token
2. 上传一份文档
3. 系统异步完成知识库入库
4. 用户对知识库提问
5. 系统返回带引用来源的回答
6. 用户再发起一个任务型请求
7. Agent 调用工具创建任务或查询任务
8. 在 Grafana 中看到请求和耗时变化

这条链路的好处是，一次演示就能同时覆盖：

- 后端接口
- JWT 鉴权
- RAG
- Tool Calling
- 异步任务
- 可观测

## 10. README 后续应围绕什么补充

如果以这份 MVP 为标准，README 后续最值得补的不是更多技术名词，而是更强的“展示证据”。

建议优先补 4 类内容：

### 1. Demo 展示区

- Swagger 页面截图
- 文档上传与问答截图
- Agent 调用工具截图或 GIF
- Grafana Dashboard 截图

### 2. 典型工作流说明

用 5 到 8 步写清楚主链路，不要只列模块。

### 3. 关键接口示例

至少保留下面几类：

- 登录
- 上传文档
- 知识库问答
- Agent 对话
- 可观测统计接口

### 4. 项目亮点总结

亮点不要堆栈名，应该强调：

- 不只是调用模型，而是完整后端系统
- 不只有问答，还能调用工具执行任务
- 不只有功能，还有监控和日志

## 11. 当前项目的 MVP 价值定位

这个项目最适合被包装成：

- `Python 后端实习项目`
- `AI 应用开发 / Agent 开发实习项目`

它的核心卖点不是“模型能力多强”，而是：

- 有标准后端工程结构
- 有真实业务对象和接口
- 有 AI 能力接入和落地
- 有异步处理和监控体系
- 有可以被演示和验证的完整链路

## 12. 一句话结论

这个项目当前的 MVP 已经不是“聊天 Demo”，而是一个可用于实习投递的 AI 后端工程项目；后续最值得补的不是更多新功能，而是围绕现有闭环补齐截图、GIF、架构图和演示说明。
